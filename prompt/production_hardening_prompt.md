# [작업 지시서] PoC → 프로덕션 수준 실무화 리팩토링

당신은 시니어 소프트웨어 엔지니어입니다. 현재 작업 디렉토리의 코드는 **아이디어 검증을 위해 빠르게 작성된 PoC(Proof of Concept)** 입니다. 이 프로젝트는 아래처럼 **이기종 분산 시스템**으로 구성되어 있으므로, 단일 앱 리팩토링이 아니라 컴포넌트별 특성을 고려한 실무화가 필요합니다.

- ① ESP32-S3 (C++/PlatformIO, Edge Impulse) — 사람 감지/캡처
- ② Raspberry Pi 5 (Python/FastAPI, Docker, ONNX YOLOv8) — PPE 정밀 판별
- ③ 클라우드 저장 로직 (Provider 추상화)
- ④ 웹 대시보드 (Next.js/Tailwind/Socket.IO) — 실시간 모니터링

이 코드를 실제 서비스(Production) 환경에 안정적으로 배포하고 유지보수할 수 있는 수준으로 고도화하려고 합니다.

## 1단계: 실무화 리팩토링 리포트 작성 (코드 수정 전, 리포트만 먼저)

프로젝트 전체(①~④) 코드를 훑어보고, 아래 항목을 기준으로 **컴포넌트별로 구분해서** '실무화 리팩토링 리포트'를 마크다운으로 작성해 주세요. 각 항목은 "어떤 컴포넌트에 해당하는 문제인지" 명시할 것.

### 1. 예외 처리 및 로깅
- 처리되지 않은 엣지 케이스, `try-catch`/에러 핸들링 누락 구간 식별
- 언어별로 적합한 로깅 방식 도입 방안 제시 (단순 `console.log`/`print` 지양)
  - ESP32(C++): Serial 로그 레벨링(DEBUG/INFO/ERROR), 크래시 시 재부팅/워치독 처리
  - RPi5(Python): `logging` 모듈 또는 `structlog` 등 구조화 로깅
  - 웹(Node/Next.js): Winston/Pino 등 구조화 로깅
- **분산 추적(Correlation ID)**: ESP32에서 최초 감지 시 생성한 `request_id`가 RPi5 → 클라우드 → 웹 대시보드까지 끝까지 로그에 남아있는지 점검. 끊기는 구간이 있다면 어디서 끊기는지 명시하고 개선안 제시

#### 1-1. RPi5(Python `logging`) 세부 점검 항목
- **Logger 레벨과 Handler 레벨은 서로 다른 관문**이라는 점을 기준으로 점검할 것: 로그가 안 찍히는 문제가 발생하면 (a) 로거 레벨에서 레코드 자체가 만들어지지 않은 것인지, (b) 레코드는 만들어졌는데 핸들러 레벨에서 걸러진 것인지 구분해서 진단하고, 코드에 두 레벨이 각각 명시적으로 설정되어 있는지 확인
- **로거 계층(hierarchy)과 `propagate`** 점검: 여러 모듈에서 로거를 생성할 때 상위(root) 로거까지 전파되어 같은 로그가 여러 핸들러에 중복 기록되고 있지 않은지, 반대로 `propagate=False`로 인해 로그가 아예 유실되고 있지 않은지 확인. 실무 권장 구성(핸들러는 root에만 붙이고, 하위 모듈은 이름만 분리)을 따르고 있는지 점검
- **로그 포맷 필수 요소** 확인: timestamp(`asctime`), 심각도(`levelname`), 로거 이름(`name`), 파일:줄번호(`filename:lineno`), 메시지(`message`) 5가지가 모두 포함되어 있는지. 메시지만 있는 `print` 수준의 로그가 남아있다면 지적
- **로그 로테이션 정책**: `RotatingFileHandler`(또는 동급) 적용 여부, `maxBytes`/`backupCount` 설정으로 디스크 사용량 상한이 명확히 계산 가능한지(보관 상한 = maxBytes × (backupCount+1)), 장기 보관이 필요한 로그(위반 기록 등)는 로컬 로테이션에 맡기지 말고 별도 로그 수집 서버/클라우드로 전송하는 구조인지 확인
- **시크릿 노출 여부**: 로그 메시지에 API 키, 토큰, 인증정보가 평문으로 출력되는 부분이 없는지 점검. (참고: 마스킹은 원본 값이 그대로 출력될 때만 동작하므로, base64 인코딩·부분 문자열 출력 등으로 우회되어 실질적으로 노출되는 경우도 함께 확인)

### 2. 보안 강화
- 하드코딩된 시크릿 키, Wi-Fi 자격증명, DB/클라우드 설정을 `.env`(또는 ESP32의 경우 `config.h`를 gitignore 처리 + 별도 secrets 관리)로 분리
- 사용자 입력값 검증(Validation) 로직 점검 (특히 ESP32→RPi5 API의 이미지/메타데이터 검증)
- RPi5 FastAPI 엔드포인트에 대한 최소한의 인증(API Key/디바이스 토큰 등) 적용 여부 점검 — 외부에서 임의로 이미지 업로드 요청을 보낼 수 없도록
- 클라우드 저장소 접근 권한(최소 권한 원칙, presigned URL 등) 점검

### 3. 코드 모듈화 및 아키텍처
- 단일 파일/거대 함수에 뭉쳐있는 비즈니스 로직을 역할별(라우터, 컨트롤러, 서비스, 레포지토리 등)로 분리 (SRP 적용)
- ESP32 코드에서도 캡처/전송/재시도 로직이 하나의 `loop()`에 뒤엉켜 있지 않은지 점검하고 모듈 단위로 분리 제안

### 4. 성능 및 최적화
- N+1 쿼리 문제, 불필요한 동기 처리 병목 구간 식별 (RPi5 추론 파이프라인, 웹 백엔드 DB 조회 등)
- **엣지 디바이스 리소스 제약**: RPi5의 CPU/메모리 사용량이 실시간 추론에 병목이 되는 지점, ESP32의 메모리/전력 제약 관련 이슈 식별
- ONNX Runtime 추론 배치 처리, 비동기 I/O(FastAPI async) 적용 여부 점검

### 5. 네트워크 안정성 (엣지 IoT 특성 반영)
- ESP32 ↔ RPi5, RPi5 ↔ 클라우드 통신 중 일시적 네트워크 단절 시 처리 방안 점검
  - 재시도(exponential backoff), 로컬 큐잉/버퍼링, 타임아웃 설정 여부
- 클라우드 업로드 실패 시 유실 없이 재처리할 수 있는 구조인지 (예: 로컬 임시 저장 후 재전송)
- 웹 대시보드의 WebSocket 재연결 로직이 실제로 견고한지 점검

### 6. 개인정보 및 데이터 처리 정책
- 사람 얼굴이 포함된 이미지를 다루는 프로젝트이므로, 최소한의 프라이버시 고려사항 점검
  - 이미지 보존 기간(retention policy) 정책 존재 여부
  - 저장소/DB 접근 권한이 필요 최소 인원으로 제한되는지
  - (선택) 얼굴 마스킹/블러 처리 필요 여부 검토 의견 제시

### 7. 배포 환경 (멀티 아키텍처 고려)
- RPi5용 Docker 이미지가 PC(x86/arm64 개발 환경)에서 테스트하고 실제 배포 시 ARM64(라즈베리파이5 네이티브)로 문제없이 전환되는 구조인지 점검
- `docker-compose.yml`/`Dockerfile`의 `platform` 설정, 베이스 이미지의 멀티 아키텍처 지원 여부 확인

### 8. 테스트 및 배포 준비
- 단위 테스트(Unit Test) 뼈대 코드 생성
  - RPi5/웹: pytest / Jest 등
  - ESP32: 하드웨어 의존성이 큰 부분은 모킹 가능한 순수 로직(캡처 판단, 재시도 로직 등)만 분리해서 테스트 가능하게 제안
- 운영 환경 배포를 위한 `Dockerfile` 초안 (RPi5, 웹 각각) 및 최소한의 CI 파이프라인 초안(GitHub Actions 등, lint+test 정도의 기본 수준) 제시

#### 8-1. pytest 작성 시 세부 점검 항목 (RPi5)
- **파일/클래스/함수 네이밍 규칙** 준수 여부 확인: 파일은 `test_*.py` 또는 `*_test.py`, 클래스는 `Test`로 시작하면서 `__init__`이 없어야 하고, 함수는 `test`로 시작해야 수집됨. 규칙에 어긋나면 **에러 없이 조용히 0개 수집**되므로("분명히 테스트를 작성했는데 실행이 안 된다" 함정), 새로 만드는 테스트 파일이 이 규칙을 지키는지 반드시 확인
- **fixture scope 선택 근거** 명시: `function`(기본값, 테스트마다 준비 → 가장 느리지만 완전히 격리) / `module` / `session`(가장 빠르지만 앞 테스트의 상태 오염이 뒤 테스트에 전파될 위험) 중 무엇을 쓸지, 왜 그 scope로 충분히 격리되는지 근거를 리포트에 남길 것
- **외부 의존성 모킹**: 클라우드 업로드, RPi5 추론 서버 호출 등 외부 API/네트워크에 의존하는 테스트는 `unittest.mock`/`pytest-mock`으로 모킹하고, 호출 인자(예: 업로드된 파일명, violation 여부)까지 검증할 것. 다만 전부 모킹으로 대체하지 말고 실제 연동을 검증하는 통합 테스트를 최소한으로 별도 유지할 것
- **CI에서 자주 쓰는 실행 옵션**을 CI 스크립트에 반영: `-x`(첫 실패에서 중단, 원인 하나에 집중할 때), `--lf`(직전 실패만 재실행, 로컬 반복 수정 시), `-k`(이름으로 필터링) 활용법을 `README.md` 또는 `docs/testing.md`에 안내

#### 8-2. GitHub Actions CI/CD 파이프라인 세부 점검 항목
- **트리거(`on`) 누락 여부** 확인: `on:`이 비어있거나 잘못 설정되면 워크플로가 영원히 실행되지 않음. `push`(브랜치 필터), `pull_request`, `workflow_dispatch`(수동 실행), `tags`(태그 push 시에만 배포 등) 중 이 프로젝트에 필요한 조합이 빠짐없이 들어가 있는지 확인. 특히 main push와 PR 양쪽에 반응하도록 구성하면 같은 커밋이 두 번 트리거될 수 있으므로 `concurrency` 설정으로 중복 실행을 정리할 것
- **matrix 구성**: 여러 Python 버전/OS 조합으로 테스트한다면 matrix 조합 수(= 각 축의 곱)만큼 동시 실행되고 그만큼 실행 시간(비용)이 소모된다는 점을 감안해 필요한 조합만 최소로 구성. `fail-fast: true`(하나 실패 시 나머지 즉시 취소, 빠르고 저렴하지만 다른 조합의 실패 여부는 알 수 없음) vs `false`(끝까지 실행, 실패 범위를 정확히 파악 가능하지만 시간 소모)의 트레이드오프를 상황에 맞게 선택하고 이유를 명시
- **`needs` 기반 파이프라인 순서**: lint → test → build → deploy 구조로 구성하고, 앞 단계가 실패하면 뒤 단계는 "실패"가 아니라 **"건너뜀(skip)"** 상태가 되어야 함(검증을 통과 못 한 코드가 배포로 넘어가지 않도록). deploy는 태그 push 등 조건(`if`)에서만 실행되도록 제한하고, 운영(production) 배포에는 `environment: production` + 승인자(reviewer) 게이트를 걸어 자동화 속도와 사람의 통제를 함께 확보할 것
- **시크릿 관리**: API 키/DB 접속정보 등은 반드시 GitHub Secrets(`secrets.*`)로 관리하고, 워크플로 로그에 값이 그대로 노출되지 않는지 확인. 단, **마스킹은 원본 값이 그대로 출력될 때만 동작**하므로 `echo "$API_KEY" | base64` 처럼 인코딩·가공해서 출력하면 마스킹이 무력화되어 그대로 노출됨 — 이런 우회 출력이 없는지 워크플로 파일을 전수 점검할 것
