# [보완 사항] 기존 실무화 리팩토링 프롬프트에 추가할 항목

> 이 문서는 `production_hardening_prompt.md`에 **새로 추가되는 부분만** 담고 있습니다. 기존 리포트 항목(1~8) 뒤에 아래 9~13번을 이어서 요청하시면 됩니다.

---

### 9. 파라미터화 및 가독성 (신규 항목)
- **하드코딩 전면 제거**: 시크릿뿐 아니라 URL, confidence threshold, timeout 값, 재시도 횟수, 파일 경로, 모델 파일명 등 모든 매직넘버/매직스트링이 설정 파일(`config.yaml`/`.env`/ESP32의 `config.h`)로 분리되어 있는지 전수 점검
- **클린 코드 아키텍처**: 모듈 간 결합도(coupling)를 낮추기 위한 인터페이스/추상화 계층이 있는지, 상위 로직이 특정 구현체(예: 특정 클라우드 SDK)에 직접 의존하고 있지 않은지 점검 (③ 클라우드 저장 Provider 패턴처럼 나머지 모듈도 일관되게 추상화되어 있는지)
- **환경별 설정 프로파일**: dev/staging/production 등 배포 환경별로 설정값(로그레벨, API 엔드포인트, DB 접속정보 등)을 분리 관리할 수 있는 구조인지 확인하고, 없다면 도입 방안 제시

### 10. 예외 처리 및 안정성 — Graceful Degradation 보강
- 기존 "예외 처리 및 로깅" 항목에 추가로, **치명적이지 않은 오류**(클라우드 업로드 실패, 웹소켓 일시 단절 등) 발생 시 전체 파이프라인이 중단되지 않고 핵심 기능(사람 감지 → PPE 판별)은 계속 동작하는 **Graceful Degradation** 구조인지 점검
- 예: 클라우드 저장 실패 시 로컬 큐잉 후 재시도, 웹 대시보드 연결이 끊겨도 RPi5/ESP32 파이프라인은 정상 동작 유지되는지 확인

### 11. 성능 및 메모리 관리 (신규 항목)
- **메모리 누수 점검**: 특히 장시간 구동되는 RPi5 추론 서버에서 이미지 버퍼, 모델 세션 등이 요청마다 정상 해제되지 않고 누적되는 구간이 없는지 점검. Python GC 관점에서 순환 참조/미해제 객체 여부 확인
- **병렬 처리**: 이미지 수신 → 전처리 → 추론 → 후처리 파이프라인이 순차 처리로 인해 지연되고 있다면, 비동기 처리 또는 멀티프로세싱으로 분리해 처리량을 개선할 수 있는지 검토
- **대용량 데이터 스트리밍**: 웹 대시보드의 실시간 영상/이미지 스트리밍 시 전체 파일을 메모리에 한 번에 올리지 않고 청크 단위 버퍼링으로 처리해 I/O 병목을 줄이는지 점검

### 12. 로깅 — 중앙 로그 스토리지 및 컨텍스트 보강
- 기존 로깅 항목(로컬 로테이션)에 추가로, 중앙 로그 스테이션(ELK, Loki, CloudWatch Logs 등)으로 로그를 전송해 ESP32/RPi5/웹 등 여러 컴포넌트의 로그를 한 곳에서 검색·모니터링할 수 있는 구조를 제안
- 에러 로그에는 역추적 가능한 컨텍스트(request_id, device_id, 입력 파라미터, 스택 트레이스)가 반드시 포함되는지 점검 — 메시지만 있는 로그는 장애 발생 시 원인 파악이 불가능함을 지적

### 13. CI/CD 파이프라인 — 4단계 흐름 명시적 구현 (기존 8-2 보강)
아래 4단계를 실제 `.github/workflows/*.yml`로 구현하고, 이 순서와 게이트 조건이 지켜지는지 점검할 것:

1. **Code Push**: 개발자가 main/feature 브랜치에 push
2. **GitHub Actions 트리거**: push/PR 이벤트 감지 시 워크플로 자동 실행 (트리거 누락 여부는 기존 8-2 항목 기준으로 점검)
3. **Pytest 자동 테스트**: 단위 테스트(Unit Test)와 통합 테스트(Integration Test)를 모두 실행하고, job/step 이름으로 두 테스트 종류가 구분되도록 구성
4. **Build & Deploy**: 3번 테스트를 에러 없이 통과한 코드만 빌드·배포로 진행. `needs: pytest` 형태의 게이트를 걸어 테스트 실패 시 빌드/배포 단계가 아예 스킵되도록 구성 (기존 8-2의 needs 기반 skip 원칙과 동일하게 적용)

이 파이프라인 구조를 워크플로 초안으로 작성한 뒤, 왜 이 순서여야 하는지(테스트 없이 배포되는 상황을 원천 차단하기 위함)를 `README.md`에 한 줄로 설명해 둘 것.
